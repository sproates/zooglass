# HA client protocol v1

A viewer must be able to reconnect to another ZooGlass process, obtain a fresh authorised snapshot and recognise data still arriving from its old connection. A producer that lost a receipt must be able to find out whether its publication committed. Both operations depend on the generation and revision checked by PostgreSQL.

**Proposed contract for the integration branch.** Storage and owner admission have real-database coverage. The routes, client behaviour and deployment settings below are requirements for the transport implementation. Two-process and proxy qualification follow separately. [Clustering design](clustering-high-availability.md) · [Current PostgreSQL boundary](../../zooglass/docs/postgresql-storage.md)

## Entering HA mode

Selecting the `ha-static-v1` deployment profile requires PostgreSQL storage, schema version 2, a nonblank runtime ID, an explicit access mode, the matching tenant binding, database connection settings and a dedicated readiness secret. Validate configuration before candidacy. Unsupported fields, mappings, controls, schema, unsafe listener or TLS settings, and conflicting durable bindings prevent serving. Preserve the stored runtime incarnation on restart. Creating a replacement incarnation after a restore requires a stopped-cluster operator procedure and a client reset.

Each candidate listens while waiting for ownership and refuses application traffic until it can prove readiness. Run one candidacy loop and one outstanding ownership operation per process. A fresh attempt must acquire, recover, build and activate in that order. Renew the recovering or active attempt against the primary. On lost or uncertain authority retire the attempt, detach subscriptions, cancel queued work, abort outstanding HTTP output where possible and close its sockets. Re-entry requires a new attempt, generation and recovery. Existing sockets cannot switch to the next generation in place.

The proposed deployment defaults are a 15-second lease, renewal every 5 seconds and a 1-second delay between candidacy attempts, with at most 250 ms of jitter. The settings must be positive and the renewal interval strictly shorter than the lease. The internal lease supports 1 to 300,000 whole milliseconds. Bound acquisition and JDBC I/O as well as the existing database lock, statement and idle-transaction waits. Timeouts and missed renewal never grant permission to continue. These are scheduling bounds, not a recovery-time claim. A permanent configuration or binding error stops candidacy until corrected. A busy owner or unavailable primary leaves the candidate unavailable and eligible for bounded retry.

## Routes and negotiation

The profile uses HTTP/1.1. On either snapshot route the client sends `Accept: application/vnd.zooglass.ha-v1+json`. A server accepts an explicit occurrence of that media range with positive quality, case-insensitively. A wildcard alone or explicit quality zero does not negotiate HA. A successful response uses that media type, `Vary: Accept` and `Cache-Control: no-store`. All application errors and readiness responses also use `Cache-Control: no-store`. Clients refuse redirects and verify the negotiated type before accepting a body.

For either WebSocket route offer the case-sensitive subprotocol token `zooglass.ha.v1` in `Sec-WebSocket-Protocol`. A successful upgrade selects exactly that token. Reject an absent or unsupported offer before upgrade. The client verifies the selected token before accepting any data. Credentials remain in the existing bearer or session-cookie mechanism. The subprotocol, URL, query and application frames carry no credential.

| Route                                                                | Negotiated operation                                                                                                                                 |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /views/{viewId}/{entityId}` or `GET /views?viewId=…&entityId=…` | One authorised snapshot or authoritative unknown-view result. A configured view with no data for the entity still returns its normal empty snapshot. |
| `GET /views/live` upgrade                                            | Viewer identity admission, then subscription commands and per-resource authorisation.                                                                |
| `GET /events` upgrade                                                | Trusted producer publications and receipts. In protected mode this route is available only on the existing authenticated loopback operator listener. |
| `POST /views`, `/progress`, `/facts/retire`                          | Static profile rejects the operation before registration, upgrade or mutation. A fact-bearing publication is also rejected.                          |
| `GET /ha/ready`                                                      | Readiness probe defined below. No application negotiation.                                                                                           |

Check connector, route boundary, Origin and required credential before revealing a protected resource or serving role. Authenticate the viewer before upgrade and authorise the requested resource before any lookup, including a lookup returning 404. Policy calls run outside the owner and grant locks. A viewer request to a protected operator route receives the existing boundary refusal. An open-demo profile omits viewer policy checks. Its HA negotiation and owner checks still apply. Standalone deployments keep their existing API. An HA client never retries with a standalone protocol after a negotiation failure. ## Admitted messages

HTTP data bodies and WebSocket text messages are UTF-8 JSON objects. A version-one envelope has exactly six members. Object member order is insignificant. Reject duplicate members, missing members, unknown kinds, wrong field types or an invalid counter before using any payload.

```json
{
  "kind": "receipt",
  "incarnation": "01234567-89ab-4cde-8012-3456789abcde",
  "generation": "18",
  "contentRevision": "9",
  "authorityRevision": "11",
  "payload": {
    "status": "duplicate",
    "reason": "alreadyCommitted",
    "stream": {
      "sourceId": "fleet",
      "epoch": "trip-1",
      "sourceEntityId": "car-1"
    },
    "publicationSequence": 41,
    "version": 6,
    "changedViews": [],
    "targets": []
  }
}
```

`incarnation` is the stored UUID in lowercase, hyphenated, 36-character form. `generation`, `contentRevision` and `authorityRevision` are canonical unsigned decimal strings up to `9223372036854775807`. Generation starts at 1. Revision zero is `"0"`. All other values match `[1-9][0-9]*`, with at most 19 digits and the same upper bound. Reject signs, whitespace, exponents, leading zeroes and JSON numbers. Compare these strings as exact integers, for example with `BigInt` after validation. Require `contentRevision <= authorityRevision`.

Content revision identifies the global installed revision at capture or commit. Authority revision identifies the global revision checked when that individual response was admitted for handoff. In the example, an unmatched publication committed at revision 6, its duplicate receipt was captured at 9 and admitted at 11. Its original version and target outcomes survive. An unchanged view may also have a last-change version below the revision of its fresh capture. The existing payloads keep their JSON numeric types. Use lossless parsing for exact payload versions or arbitrary application numbers. A client orders owner generations and captures using the envelope counters.

| Kind                 | Where                                        | Exact payload                                                                                                                                                                                                                                                  |
| -------------------- | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `hello`              | First server frame on either upgraded socket | `{}`. Checked active generation and revision for this connection. Clients wait for it before sending requests or retrying a publication.                                                                                                                       |
| `snapshot`           | HTTP 200                                     | The public snapshot object with `viewId`, `entityId`, `version`, `data`, `provenance`, `publicationSequences` and `status`. Use the existing public projection, including empty and pending views.                                                             |
| `notFound`           | HTTP 404                                     | `{}`. The named view is absent at the checked capture after authorisation. This is the only negotiated HTTP resource-miss representation.                                                                                                                      |
| `subscribed`         | Viewer socket                                | `{"subscription":"1","viewId":"…","entityId":"…","recovery":"freshSnapshot"}`. Acknowledges admission to the requested resource.                                                                                                                               |
| `baseline`, `update` | Viewer socket                                | `{"subscription":"1","snapshot":S}` where `S` is the complete public snapshot object used for HTTP 200. The envelope kind identifies its role.                                                                                                                 |
| `unsubscribed`       | Viewer socket                                | `{"subscription":"1","viewId":"…","entityId":"…"}`, after removing that membership.                                                                                                                                                                            |
| `requestError`       | Viewer socket                                | Exactly `{"code":"invalidRequest","subscription":null}` for malformed or unsupported commands, or `{"code":"unknownView","subscription":"1"}` for an authorised current lookup, echoing the requested subscription ID.                                         |
| `receipt`            | Source socket                                | Existing publication outcome with `status`, `reason`, `stream`, `publicationSequence`, `version`, `changedViews`, `targets`. New success is `committed/postgresql`. Retained retries are `duplicate/alreadyCommitted` and retain original version and targets. |

The receipt example has an empty target list because the publication matched no view. Every matched target retains its original field outcomes. Invalid envelopes receive the existing malformed rejection with null identity and version if the service can obtain a current checked handoff. An uncertain commit or failed handoff closes the connection without manufacturing a success, rejection or rollback receipt. [Publication and receipt fields](../../zooglass/docs/publications.md)

## Opening a subscription and admitting output

Subscribe with `{"action":"subscribe","subscription":"1","viewId":"…","entityId":"…"}`, optionally adding `"recovery":"freshSnapshot"`. The client assigns a fresh subscription ID to **every** subscribe attempt. IDs start at `"1"`, increase strictly on that socket and use the generation counter grammar above. Keep only the last issued ID and current memberships. Close and reconnect before ID exhaustion. Each acknowledgement, baseline, update and subscribe refusal echoes that ID. Unsubscribe with `{"action":"unsubscribe","subscription":"1","viewId":"…","entityId":"…"}` naming the active membership. Reject an unknown or mismatched ID, cursor, unsupported recovery mode, extra property or invalid identifier. The client serialises commands until the reply, waiting through the baseline on a successful subscribe. Multiple live resources may share a socket.

After fresh policy admission, the owner checks the current grant and the exact cache revision. Under the coordinator's ordering of commits, capture the public baseline, attach the subscription generation and enqueue `subscribed` followed by `baseline` as one protected queue admission. An intervening commit must either appear in the captured baseline or be eligible for subsequent delivery. Never leave a snapshot/membership gap. The two envelopes have the same content revision, but each receives its own permit and can have a different authority revision. A close between them leaves the subscription incomplete.

A new subscribe for an already active resource replaces its membership and opens a fresh baseline under the new ID. The client invalidates the old ID when sending the request and rejects old callbacks even for the same resource. Unsubscribe cancels unsent frames for the old membership before acknowledging it. A transport write already admitted may arrive before that acknowledgement. After the acknowledgement no old-membership frame may follow it on that socket. Discard frames for a retired membership and preserve the configured delivery policy for the others. FIFO can deliver revision 7 when 8 has already committed. Coalescing may replace waiting ordinary updates for the same subscription generation. It cannot replace an acknowledgement or baseline.

Mint one immutable captured frame per recipient from the actual checked snapshot, control outcome or committed transition. Project the public payload before retaining it. Bind the frame to its source socket or viewer socket, subscription/resource generation and owner attempt as applicable. Account for the complete encoded envelope in the existing queue limits, reserving the maximum width of the authority fields where they are filled at handoff. Sharing immutable payload bytes among recipients is possible, but each handoff needs its own single-use capture. The internal coordinator snapshot contains retained contributions and must not be serialised as the public payload.

At handoff, require the original owner attempt and generation to remain active under the database row lock, and its cache revision to match the primary. The checked revision must cover the captured revision. Consume the single-use permit before submitting the immutable message. For a protected socket recheck the current identity, grant, resource and membership at native submission. No database transaction spans policy I/O, a callback or a socket wait. If a grant expires between the database permit and submission, discard that frame. For HTTP one permit binds the whole immutable response, including an authorised 404. The grant remains a separate requirement for every nonblocking chunk and for releasing empty response metadata. Abort a partially sent response on loss or expiry. Clients discard incomplete responses.

Previously admitted bytes may reach a client after takeover. A new permit on the former owner must fail even while its listener remains reachable and a proxy still considers it healthy.

## Failures and close codes

Unnegotiated HTTP failures and failed upgrades have an empty body, no ownership metadata and no resource data. Apply the protected listener boundary first. On an allowed route use the following responses.

| Condition                                                                                                                                         | HTTP response or WebSocket action                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Missing/invalid viewer credential, operator credential or forbidden Origin                                                                        | Existing protected boundary status. Viewer unauthenticated is 401, denied is 403. An invalid loopback operator request is 403.                                                                                                                                                                  |
| Wrong HTTP version on HA data routes                                                                                                              | 505 before upgrade or snapshot output.                                                                                                                                                                                                                                                          |
| Missing/unsupported HA media type or subprotocol                                                                                                  | 406 before application data or upgrade.                                                                                                                                                                                                                                                         |
| Invalid snapshot parameters                                                                                                                       | 400.                                                                                                                                                                                                                                                                                            |
| Static profile control or registration on a permitted listener                                                                                    | 405 for `POST /views` with `Allow: GET`, 404 for a control upgrade that has no HA endpoint.                                                                                                                                                                                                     |
| No active owner, failed authority check, unavailable policy or incomplete recovery                                                                | 503 before upgrade or HTTP commitment. An already committed HTTP response is aborted.                                                                                                                                                                                                           |
| Missing view after policy and current capture                                                                                                     | Negotiated 404 `notFound` on HTTP or admitted `requestError/unknownView` on the socket.                                                                                                                                                                                                         |
| Invalid text viewer command on an otherwise usable socket                                                                                         | Admitted `requestError/invalidRequest`. No copied text or exception details.                                                                                                                                                                                                                    |
| Denied or unavailable replacement of a resource already active on this socket, loss/expiry of a current grant, or a grant for a different subject | Invalidate the whole socket's memberships before cleanup and request close 1008. No subsequent resource handoff can use those grants.                                                                                                                                                           |
| Denied or unavailable subscribe for resource B with no current B membership on this socket                                                        | Reply to B with exactly `{"error":"accessDenied","subscription":"1"}` or `{"error":"accessUnavailable","subscription":"1"}`, echoing its validated ID. Preserve existing valid memberships for other resources, including A. The refusal carries no owner metadata or resource-existence claim. |
| Owner loss, ambiguous processing/commit, failed permit or bounded service wait after upgrade                                                      | Close 1013, if possible. The peer may observe only transport loss.                                                                                                                                                                                                                              |
| Queue returns FULL or writer fails                                                                                                                | Request 1013. FULL can also indicate a stopped queue.                                                                                                                                                                                                                                           |
| Oversized frame or opening batch                                                                                                                  | Request 1009. Binary application message on a text socket requests 1003.                                                                                                                                                                                                                        |

The two fixed subscription refusal objects are the only application messages outside the success envelope on a negotiated socket. Accept them only on a viewer connection with a pending subscribe. Never apply them as owner metadata, a baseline or a receipt. Errors use fixed codes, contain no caller-controlled text, and fit in 96 UTF-8 bytes outside an envelope. Close requests use empty reason text. Close codes convey no peer acknowledgement and cannot establish a publication outcome.

## Client recovery

Configure a client for one logical deployment and either two named candidate origins or one stable proxy origin. The same client handles HTTPS snapshots and WSS in both modes. It keeps the pinned incarnation and highest accepted serving generation for that deployment. A new client establishes its initial pin from a verified `hello` or an authorised complete HTTP 200 or 404. A client resuming a source spool must use the spool's existing pin.

1. **Start an attempt.** Allocate a new local connection epoch even when reconnecting to the same URL or owner generation. Cancel previous HTTP reads, retry timers, pending commands and socket handlers. Clear protected snapshots on loss of access or connection. Retain desired subscriptions as identifiers only.
2. **Validate the response.** First check that its socket or request still belongs to the current local epoch. Verify negotiation, schema, counter bounds and expected kind. Discard completions from obsolete attempts, including errors and close notifications. A different incarnation stops recovery. Clear displayed viewer data and retire pending network operations. Preserve every unacknowledged publication's original bytes, identity and spool incarnation pin, and report its outcome as unresolved. Resuming viewer reads requires an explicit application/operator reset to the replacement deployment. The producer separately requires an application reconciliation decision about the old spool. A viewer reset cannot discard or repin it. Never order UUIDs or replay old-incarnation publications automatically.
3. **Observe ownership.** Reject a lower generation than the watermark shared by HTTP and WebSocket for this incarnation. A higher generation retires all older connections and reads and clears their subscription baselines. A new socket establishes its generation from its own `hello`. Every subsequent admitted frame on that socket must match it. If a newer HTTP response reveals takeover, establish a new viewer socket and fresh subscriptions.
4. **Open each desired resource.** Send a fresh subscribe, require its matching `subscribed`, then its `baseline` at the acknowledgement's content revision. Only that baseline makes the subscription live. Compare socket epoch, subscription ID and resource on every callback. Discard obsolete IDs. If the current membership receives an update before its baseline, an inconsistent acknowledgement, or a decreasing content revision, abort and resubscribe. Buffer no pre-baseline updates. Each resource follows its own FIFO or configured coalescing behaviour. A different view advancing to revision 12 cannot invalidate a permitted frame at 11 for this view.
5. **Complete HTTP reads independently.** Tag each request with local connection epoch, resource, a per-resource read sequence and the resource's current presentation epoch. Supersede earlier reads when a later read starts. Retire the presentation epoch when a subscription is replaced, a live baseline/update is applied or the resource is cleared. Before exposing any success, absence or error, check these tags and the current generation again after the entire body has arrived and parsed. A standalone HTTP lookup can display its own current result. A live subscription uses its own baseline and ordered updates. An HTTP completion cannot initialise that subscription, overwrite a newer live value or clear it with a delayed 404.

The reusable client has one connection attempt and one retry timer per endpoint role, one pending viewer command per socket and at most one active HTTP read per desired resource. The caller sets a finite resource count and byte limit for inbound HTTP/WS messages. Reject excess requests before creating state, bound streaming reads, refuse an oversized frame and discard its incomplete data. Store one accepted value per desired resource, an active membership ID and its revision. Do not retain old sockets, generations or a frame history to detect stale callbacks.

The reference reconnect policy tries each configured candidate in round-robin order, or the same stable origin on every attempt. Each connect, `hello`, opening baseline or HTTP read has a 5-second deadline within a 30-second recovery episode. After failure wait 250 ms, 500 ms, 1 s, then 2 s between later attempts, clipped to the remaining episode. On exhaustion report unavailable and stop. An explicit retry starts another episode. Cancellation retires the epoch immediately. Known credential refusal, certificate failure, protocol incompatibility or incarnation mismatch stops automatic retry. A browser may expose only a generic failed handshake. Its bounded episode can expire without diagnosing the cause.

## Retrying a source publication

Before sending on an authenticated/negotiated source socket, match the current `hello` to the intended runtime incarnation. Send the existing publication JSON directly as one text frame. Keep the original UTF-8 message and its identity through a timeout, connection loss or unconfirmed receipt. Resend the same bytes to the next authorised owner. Regenerating a sequence number, epoch or numeric payload can change the outcome. Validate the returned stream tuple and publication sequence before completing the caller's pending operation.

The reference producer starts a 30-second operation deadline when it accepts a publication. Each send has a 5-second receipt deadline starting at transport submission. Connect, `hello`, receipt waits, backoff and every resend share the remaining operation budget. A new `hello` never restarts that budget. On a receipt timeout retire the socket epoch and retry the retained bytes while time remains. The producer holds one unacknowledged publication at a time within its configured finite byte limit. Extra submissions receive local backpressure. A successful retained retry returns the original targets even if the view has since changed. `identityConflict` and `outsideRetention` require application reconciliation. Neither authorises an automatic retry with a new identity. The producer surfaces an unresolved outcome when its recovery deadline expires. Durable spooling across producer or host loss belongs to the application. In protected deployments the trusted source fixture retries via the successor's local operator listener. Viewer credentials and the viewer proxy cannot grant source access.

## Readiness and the stable viewer address

Reserve the exact path `GET /ha/ready` on the HA viewer TLS listener for both qualified access modes. The route accepts HTTP/1.1 and one `Authorization: Bearer <probe-token>` header. Use a separately configured, randomly generated token with at least 32 token characters. Compare it without exposing timing differences from the secret's matching prefix. Refuse duplicate or invalid credentials. Configure a different secret from the operator and policy-service credentials and keep it out of application clients, URLs and routine logs. Bind this exception to the actual probe handler on the intended connector. A prefix match or a forwarded header cannot open another route.

Every probe response is empty, with `Content-Length: 0` and `Cache-Control: no-store`. Missing, duplicated or incorrect probe credentials receive 401. An authenticated wrong method receives 405 with `Allow: GET`. An authenticated valid request receives 200 only after a fresh bounded check of active attempt, unexpired lease and matching installed revision against the primary. Otherwise return 503. A probe timeout or non-success removes a backend from consideration. The route returns no role, generation, tenant, snapshot or ownership detail. The actuator and operator listener remain private.

The probe has one absolute 2-second monotonic deadline from receipt to response. Try to reserve the same exclusive operation gate used by mutations, renewals and handoffs. If another operation holds it, return 503 immediately without starting a database check, queuing a worker or cancelling the operation in progress. Only the probe holding the gate may use that owner's connection. It must issue a new check for this request.

Bound each database lock wait, statement, network read and commit by the **remaining** deadline. The normal 3-second database lock timeout and 10-second statement timeout exceed the probe budget. On expiry return 503, cancel the probe's own outstanding operation and retire the attempt and its connection if the transaction outcome is uncertain. Hold the operation slot until that operation and bounded cancellation/connection cleanup settle. Further probes receive 503 during cleanup. A late result cannot mark the candidate ready or admit another operation on that connection. Reacquisition after retirement uses a fresh attempt and connection. Qualification must exercise both a busy local owner and a probe blocked in PostgreSQL.

For direct access, configure a trusted origin and valid certificate hostname for each candidate. For the stable address use one viewer origin, for example `https://views.example` for HTTP and `wss://views.example/views/live` for live delivery. HAProxy forwards the client's TLS connection at TCP level to a serving-ready backend. ZooGlass terminates TLS and keeps forwarded-header trust disabled. Its certificate must validate for the stable name and the direct name(s) used for that backend. The proxy's own HTTPS probes validate a configured backend hostname against a trusted CA and authenticate with the dedicated probe token. Credentials for viewers remain subject to ZooGlass's Origin, cookie or bearer checks. Direct and proxy qualification use the Node.js reference client. That client sends credentials only to its explicitly configured trusted origins and can set its own bearer header. A browser WebSocket cannot supply that header. Use the approved session cookie and matching Origin for browser WSS. Cross-origin browser HTTP also requires an application-approved CORS policy, including credentialed requests and preflight where applicable, and suitable cookie scope and SameSite settings. The direct-client qualification does not establish cross-origin browser support. The stable same-origin deployment avoids that additional dependency.

Use only the viewer ports as proxy backends. Never forward the protected loopback operator listener, replay requests, retry publications on the proxy or migrate an open connection between backends. A TCP passthrough proxy with no healthy backend can close or fail the TLS connection within its configured connection bound. An HTTP status is possible only after a TLS endpoint accepts the connection. Conversely, a formerly healthy backend can remain reachable behind stale routing. Its own authority check still has to refuse fresh work after takeover. The direct and proxy cases, including delayed HTTP and WebSocket completions, require real-process qualification before deployment claims.
