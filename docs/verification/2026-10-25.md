# Verification review before readability refactoring

This review asks whether the current tests give us enough protection to start
refactoring ZooGlass and Workbench for readability. The recommendation is yes,
subject to maintainer acceptance of this review. The evidence covers the current
prototype's main behavioural contracts and failure paths. It does not establish
production readiness or cover capabilities that we haven't built.

## What was checked

`node_modules`, compiled outputs or coverage reports. Maven dependencies and the

## Coverage comparison

The initial baseline used production code at `13aba66`. The measured Java,
Workbench and vehicle-client production sources are unchanged between that
commit and `c7ed8cf`. This makes the line comparison useful, although V8 branch
counts still vary with execution. Figures below are local measurements with the
same report configuration, not live status or minimum thresholds.

| Scope | Initial lines | Current lines | Initial branches | Current branches |
| --- | ---: | ---: | ---: | ---: |
| Java suite / production Java | 280/345 (81.16%) | 282/345 (81.74%) | 113/167 (67.66%) | 115/167 (68.86%) |
| Standard suite / Workbench Node code | 1,986/2,901 (68.45%) | 1,986/2,901 (68.45%) | 479/591 (81.04%) | 484/594 (81.48%) |
| Browser suite / Workbench Node host | 76.38% | 2,216/2,901 (76.38%) | 69.64% | 378/541 (69.87%) |

Java gained two covered lines and two branches. Workbench's line percentages
are unchanged even though the standard suite grew from 50 to 68 tests and the
browser suite from 19 to 32. Most of the new protection comes from checking more
orderings, failures and outcomes along paths that already executed. An increase
in assertion strength need not increase line coverage.

The Java report still shows only 9/20 branches in the live-view request handler
and 8/16 in the source event handler. The broadcaster moved from 19/36 to 20/36.
The new real-service protocol tests run separate JVMs from Workbench, outside
JaCoCo's Java-suite measurement. Their successful assertions are evidence, but
we cannot turn them into a higher Java coverage figure.

The two Node scopes must not be added or averaged. Resource and engine probes
are also separate runs, not included in these coverage figures. Browser-executed
app and bridge JavaScript still has behavioural tests without line/branch
instrumentation.

## Do the assertions catch regressions?

Two temporary source changes were made separately in this checkout. Both compiled
and failed behavioural assertions. Neither change is included in the PR.

| Deliberate regression | Focused check | Observed failure |
| --- | --- | --- |
| In `ViewStore.applyLatestBySequence`, change the comparison from `<= 0` to `< 0`, allowing equal sequences to replace state and emit changes | `./mvnw --batch-mode -Dtest=ViewStoreOrderingTests -Dordering.seed=17 test` | All three selected checks failed. Seed 17 first failed at prefix 14; the duplicate permutation and equal-sequence conflict checks also rejected the change. |
| In the vehicle client's message handler, remove `socket !== current` from the early return guard | Build the browser app, then `npx tsx --test test/browser/reconnection.test.ts` | Both snapshot-arrival-order cases failed with `Old socket overwrote retained position`; the other four cases passed. |

The original source was restored after each experiment. Clean Maven verification
then passed all 80 tests, and the rebuilt browser passed all six reconnection
checks. These experiments show that specific assertions detect specific faults;
they are not a mutation-testing score or proof that every regression is caught.

## Remaining gaps and refactoring constraints

- The simulator entry point `src/index.ts` is unexecuted in both Node reports.
  Automatic-demo control/error paths are only partly covered (63.71% lines and
  35.71% branches in the browser-host report). Add focused CLI and interruption
  checks before changing those paths substantially.
- Java configuration-load failures, some validation branches and broadcaster
  write/close error handling remain incompletely measured. Existing transport
  checks cover some related behaviour, but not every exception path. Any refactor
  of these branches should identify its protecting test or add one first.
- Seeded ordering and controlled lifecycle tests cover bounded cases. They do not
  enumerate all interleavings, fuzz arbitrary schemas or minimise a failing seed
  beyond its first failing prefix. Preserve reproducible cases and the independent
  reference model when reorganising tests.
- Resource workloads verify ownership and bounded behaviour. They do not measure
  retained heap, establish capacity or prove the absence of leaks over long runs.
  History remains unbounded. Reflection-based Java cleanup assertions will need
  careful revision if internal ownership changes; keep the observable guarantees.
- Browser rendering tests protect this demo, not users' own UIs. The documented
  native OS and engine probes are deliberately limited; they do not imply mobile
  Safari coverage or a complete platform support matrix.
- Fault-gate simulation, automatic retry, permissions, persistence and retention
  policy remain feature work. Their absence must stay visible during refactoring.

Proceed with a responsibility and complexity review before moving code. Each
refactor should preserve the existing contracts, retain readable independent
assertions and run the suites affected by its boundary changes. If that review
exposes an important unprotected path, add its regression check before extraction.
Acceptance of this review permits that next stage; it does not close the remaining
vehicle-demo programme or declare ZooGlass ready for production.
