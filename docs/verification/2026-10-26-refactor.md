# Readability refactor acceptance

The planned service, Workbench, client and test extractions are delivered. This
review records the resulting boundaries, the checks run against them and the
remaining limitations. It recommends closing the readability refactor, without
claiming that every function is small or that the prototype is production-ready.

The reviewed source is `fac4a3fd1eb5592a57d0fa93895a338a463984c4`, after PRs
#48–#58. The [original responsibility review](../plans/readability-refactor.md)
and [pre-refactor verification review](2026-10-25.md) provide the comparison.
This acceptance change updates documentation only; production code and tests are
unchanged from that reviewed commit.

## Responsibilities and reuse

| Boundary | Result and evidence |
| --- | --- |
| Java projection | `ViewStore` owns state and synchronisation. `ViewDefinitions` loads and validates configuration; `FieldUpdates` implements ordering policies. Seeded ordering, equal-sequence, defensive-copy and configuration tests pass. |
| Java delivery | `LiveViewBroadcaster` coordinates subscription changes and queue insertion. `SubscriptionIndex` owns both lookup directions; each `OutboundWriter` owns its queue/task. Failure callbacks identify the writer instance, and transport I/O stays outside the coordinator monitor. Queue-limit, stale-writer and failure-cleanup checks pass. |
| Workbench execution | Scenario parsing has separate model, view and timeline modules. `ScenarioSession` owns source connections and supplied client executors; HTTP operations and step grouping are separate. Cancellation precedes disposal and overlapping actions are rejected. |
| Browser host and bridge | The host receives assets and client identity. The shared bridge receives a client factory and presentation callbacks. Neither embeds vehicle assets, IDs or DOM selectors. The inventory fixture uses the same host, bridge and executor, including a real browser check. |
| Vehicle demo | `vehicle-browser`, `vehicle-demo` and `vehicle-run` supply vehicle bindings and resource composition. `subscription-client` reports through callbacks; the small `vehicle-client` binds those callbacks to presentation. The protocol code remains in the vehicle browser build; this is not a packaged general client SDK. |
| Independent checking | Core tests run without the vehicle build or browser binaries. The all-scenario test executes non-vehicle fixtures, including order fulfilment and sports betting, through real ZooGlass. Browser receipt and rendered-demo checks remain separate evidence. |
| Test organisation | Controller lifecycle, playback and interventions have separate files, as do scenario ownership and service-process tests. Small helpers provide fixtures, gates and cleanup. Expected results remain at the test site; they do not reuse the production projection algorithm. |

The runtime relative-import graph of the reviewed TypeScript modules has no
cycles. Manual inspection also checked the browser bootstrap, configuration
bindings and the independent rendered oracle. This is a dependency review, not
a claim that static import scanning proves lifecycle correctness.

## Remaining large functions and justified exceptions

Line counts include comments and blank lines. No reviewed production or test
file exceeds 400 lines, but several closure-based factories remain long. The
function count includes their nested handlers; it is not a count of one straight
line execution path.

| Module | Size and decision |
| --- | --- |
| `demo-controller.ts` | 340 lines; factory 306, reset 70, play 62. Keep cursor, current generation, active operations and replacement/cleanup ownership together. Pure step planning is extracted. The six-boundary race matrix protects this state machine. Further splitting should follow a concrete ownership problem. |
| `browser-host.ts` | 301 lines; factory 288, upgrade handler 80. Asset/control/data handlers share one host lifetime. Explicit socket/upstream sets and one close path make teardown traceable. It remains a dense review target; a future fault gate must not become another unrelated responsibility in this closure. |
| `subscription-client.ts` | 220 lines; command execution 138. Socket generation, acknowledgement and subscription state remain together. Presentation is injected. Controlled callback/error cases and real reconnection tests protect the boundary. |
| `vehicle-observer.ts` | 199 lines; rendered-check closure 152. Page reading, independent comparisons and bounded polling remain adjacent. This is the clearest remaining readability compromise: the embedded page expression is substantial. It is demo-specific and does not leak into core execution; further extraction is not required to preserve that boundary. |
| Session and composition factories | `zooglass-session` is 199 lines with a 152-line factory; scenario, browser and vehicle-run factories span 87–98 lines. They keep acquisition, cancellation and release order visible. No general resource-management framework was introduced. |
| Parser functions | `parseScenario` is 83 lines; timeline dispatch and view parsing are 60 each. They are ordered validation stages with specific error messages. Typed entry helpers replace the previous large timeline parser. |
| Browser protocol handlers | The bridge factory is 117 lines; its message handler is 73. The browser executor factory is 131, with a 63-line execute method. Command identity, pending completion and failure reporting remain local to their protocol owner. |
| CLI and asset composition | The automatic demo, interactive CLI and vehicle composition functions span 72–87 lines. They primarily bind dependencies and express shutdown policy or explicit asset maps. |
| Larger test groups | Subscription-client unit tests: 291 lines; browser reconnection: 287; Java functional tests: 242. Each groups related observable behaviours. Their setup is explicit, and assertions remain close to the action. |

For comparison, `ViewStore` fell from 256 to 113 lines and the broadcaster from
220 to 143. Their extracted collaborators are 49–96 lines. The 512-line scenario
module is now a 124-line entry point with cohesive parsing modules, the largest
239 lines. These counts describe the result; reducing them was not itself the
acceptance criterion.

Configuration validation and field policies now have complete Java line coverage;
handler branches remain partial. Standard and browser scopes must not be added
or averaged. Browser-executed app/bridge code and controlled VM-loaded modules
remain outside these Node source reports.

The new type-only `scenario-model.ts` contributes 94 zero-hit lines under c8's
existing `all` setting. Demo-only modules also remain in the standard report even
though the core command deliberately does not launch a browser. These effects
help explain the denominator change. No exclusions were added to improve the
percentage. `vehicle-run` has 93% lines in the browser-host report; automatic-demo
lines remain 61.29%, with controlled failure/interruption tests supplying separate
behavioural evidence. The simulator CLI smoke check above is outside coverage,
so `index.ts` remains zero in the reports. V8 branch counts and exercised failure
paths can vary between runs; this checkout's figures are a measurement, not a
threshold or a guarantee.

## CI cost and remaining risks

[PR #58](https://github.com/sproates/zooglass/pull/58) removed duplicate core test
execution and per-job Linux browser package installation, aligned Maven caches
inside the prepared browser image, and initialised the wrapper before parallel
service starts. It also cancels obsolete PR revisions while preserving both
running and pending main-push runs. Its final implementation run's longest job
was 2m53s; the concurrency-review revision took 3m6s. Shared-runner and network
variation remain. Small changes must not accumulate unnecessary verification work.

The wrapper fix addresses a distribution-unpacking race. A separate earlier
observation involved concurrent Maven compilation of the shared service target.
The fresh, uncompiled core run in this review passed, but that does not prove the
compilation race impossible. It remains a known harness risk; a repeat must be
investigated rather than hidden by retries. This review does not claim a fix.

Other limits remain as recorded in the verification guide: bounded resource and
ordering cases are not exhaustive; history retention is unbounded; no production
capacity claim follows from the tests. Unexpected data-path faults, automatic
retry, permissions, persistence and retention policy remain feature work.
