# Order demo acceptance record

This proposes final acceptance of the bounded Order demo on the combined Order
and Sports delivery branch. Merging this acceptance change records approval of
both Order modes and the evidence below; it does not deliver the combined programme
to main or accept the later live Sports implementation.

Runtime baseline: `2837dc5`, after the recovery/access delivery in
[PR #162](https://github.com/sproates/zooglass/pull/162). That PR's reviewed head
`a15aff8` passed all eleven jobs in
[its final CI run](https://github.com/sproates/zooglass/actions/runs/43291714899).
This acceptance change strengthens tests and documentation; it adds no runtime
behaviour or Java projection code.

## State and queue bounds

| Scope | Bound and evidence |
| --- | --- |
| Order population | Six reused synthetic entities and two configured views: twelve persisted view/entity rows after 50 cycles. There is no growing list of orders. |
| Source identities | 30 normal source/entity streams plus one fixed unmapped payment diagnostic; `maxStreams` is 64 and each stream retains at most 128 receipts. The soak inspects the retained rows and receipt counts. |
| Progress | Tracked streams configure at most 64 received and 64 missing ranges. This schedule retains at most two received ranges and one missing range; the original payment gap eventually becomes expired evidence. |
| Contributions | Each summary has four fields, tracking three. Each delivery field retains two courier candidates; each other field has one source candidate. No unbounded history field is used. |
| Producer work | Events are generated by tick; previous-cycle retries are reconstructed deterministically. There is no delayed-event backlog. Sends await receipts one at a time; five source sockets plus one progress socket are owned and closed. |
| Page state | Twelve latest snapshots, up to twelve first-baseline observations per connection and a bounded 20-entry simulator notice feed. There is no per-update browser history in the shipped UI. |
| Delivery | ZooGlass defaults to 128 queued messages and 1 MiB per connection. The proxy has no replay buffer and closes routes with more than 1 MiB pending output; its 1 MiB frame limit can admit one further frame before the next pending-output check. These are per-connection limits, not a global viewer cap. |
| Interactive controls | At most 16 control connections, two pending commands per connection, a 1,024-character ordinary-command limit and a 64 KiB recovery-observation envelope. Recovery evidence is bounded by a 30-second deadline. |

Queue settings and overflow behaviour are shared runtime contracts, exercised by
[slow-receiver acceptance](../../workbench/test/concurrent-clients.test.ts) and the
[bounded queue tests](../../zooglass/src/test/java/io/zooglass/delivery/OutboundQueueTests.java).
The Order soak establishes retained-state counts, not peak heap use, a disk-size
plateau, throughput or an unlimited-viewer guarantee. SQLite inspection happens
after shutdown because the running service owns an exclusive store lock.

## Reproduce the focused checks

Use Node 26 and JDK 25. Install Workbench dependencies and Playwright browsers as
in the [Order guide](../../demos/order-tracker/README.md). Prepare the service
explicitly if no current JAR exists; none of these tests invokes a Java build.
From `workbench/`:

```sh
npm run build:browser
npx tsx --test test/scenarios/order-simulation.test.ts test/scenarios/order-extension.test.ts
npx tsx --test test/browser/order-browser.test.ts
npx tsx --test test/browser/order-interactive.test.ts test/browser/order-recovery.test.ts test/browser/order-protected-access.test.ts
```

The final local acceptance run passed the three-cycle source/browser checks,
50-cycle retained-state check, extension fixture and desktop/phone engine cases.
Existing recovery/protected coverage is backed by the reviewed delivery's green
CI; it is not presented as a new full local rerun here.

## Limits retained at acceptance

This is synthetic source data and a six-slot demonstration. It does not establish
production integrations, customer value, full accessibility, physical-phone
qualification or verification on every historical minimum browser version.

Views contain independently progressing contributions, not an atomic business
transaction. Required inputs govern first presence, freshness is receipt age,
and neither a stale source nor a missing report proves operational failure.
Reconnect delivers current snapshots, not all missed events. Restarting the
producer process against retained identities remains unsupported. The protected
fixture demonstrates application-supplied access decisions and client clearing;
it is not a login product. Sports integration, SSE, clustering and a general
configuration editor remain outside this acceptance.
